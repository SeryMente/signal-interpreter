# Signal Interpreter 0.10.42 — autorización del popup Auto-Answer

## Causa raíz

La versión empaquetada desde el repositorio declara `extension/ui/popup.html`, mientras que el manifiesto de la carpeta que Chrome carga directamente declara `ui/popup.html`. `presence-guard.js` comparaba el remitente exclusivamente contra la primera ruta. Por ello rechazaba tanto la consulta de estado como la orden explícita de armado con `popup-only`; el popup volvía a representar presencia desarmada.

## Corrección

- La identidad del popup autorizado ahora se obtiene de `chrome.runtime.getManifest().action.default_popup` y se resuelve mediante `chrome.runtime.getURL()`.
- La autorización sigue exigiendo ID propio de la extensión y ausencia de pestaña remitente. Una página interna distinta al popup declarado permanece bloqueada.
- La solución acepta las dos estructuras reales: raíz del repositorio y carpeta de extensión empaquetada/instalada.
- No se cambió la política OPI/VRI, el Connect guard, el comportamiento de llamadas ni Native Messaging.

## Instalación y aceptación

La carpeta activa de Chrome recibió únicamente `manifest.json` (0.10.41 → 0.10.42) y `presence-guard.js`. La clave/ID de extensión permanece igual. Ambos archivos 0.10.41 se respaldaron y cotejaron por SHA-256 antes de escribir. Respaldo: `Desktop/SI-backups/SI-0.10.41-before-0.10.42-popup-path-fix-20261107`.

Chrome no fue recargado desde RDC. El operador debe pulsar Reload en `chrome://extensions` y confirmar nuevamente «Estoy disponible»; la recarga borra la autorización efímera de `chrome.storage.session`. La prueba funcional siguiente requiere una llamada entrante OPI normal. No se generó, aceptó ni manipuló ninguna llamada real durante este ciclo.
